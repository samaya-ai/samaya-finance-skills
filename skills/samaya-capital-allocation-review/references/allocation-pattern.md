# Allocation pattern and execution (optional section)

Moved out of `SKILL.md` to keep it lean; read it when the section is elected.

## ALLOCATION PATTERN AND EXECUTION — optional section, confirmed activity only

Assesses what the recorded activity says about the team's allocation discipline. Retrieval-bound
throughout: every element is built only where the underlying figures are disclosed, and omitted
with a stated reason where they are not. Nothing is estimated, and no multiple is inferred from a
transaction value alone. When selected, this section runs after the activity log and before the
conclusion.

Four components, each run only where the data supports it:

- **Multiples paid in context.** For each acquisition where the multiple is disclosed, set it
  against the acquirer's own trading multiple on the same basis at the announcement date, **in
  adjacent columns with the difference in turns beside them**, per the side-by-side rule above. Where the
  target is listed, add the premium to the undisturbed price. Where either side is unavailable,
  state the disclosed multiple alone and mark the comparison as not retrievable — never construct a
  multiple from consideration plus an estimated earnings figure.
- **Buyback execution.** For each programme in the window, compare the average price paid, where
  disclosed, against the average price over the same period **in adjacent columns with the
  difference in percent**, stating whether volume-weighted or simple. Note stated programme size against amount executed. Where average price paid is not
  disclosed, say so rather than deriving it from spend and share count unless both are given for
  the identical period.
- **Reversals and round trips.** Flag any disposal of an asset previously acquired, with both
  dates, both values where disclosed, and the holding period. State the direction plainly; do not
  characterise intent.
- **Cadence.** Count transactions by type and year to establish whether the pattern is serial,
  episodic or opportunistic. Report the counts and distribution; do not label the team beyond what
  the counts support.

**Hard rules for this section.** Confirmed activity only — reported and unconfirmed items are
excluded from this section entirely. Every figure carries its Samaya provenance link. Where fewer
than three transactions of a type fall in the window, state that the sample cannot support a
pattern read rather than reading one. This section assesses execution against disclosure; it does
not issue a verdict on whether the allocation created value, which would require a
return-on-capital analysis beyond the scope of this review.
